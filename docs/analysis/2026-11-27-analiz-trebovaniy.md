# Анализ требований заказчика и соответствие проекта (27.11.2026, v0.47)

Источники — `docs/brief/` (постоянные инструкции, контекст проекта, роль эксперта, мастер-промт кинорежима)
и комплект чертежей раздела ПТ (PDF, 18 листов; в публичный репозиторий не включён — см. раздел 6).

Обозначения статуса: **есть** — реализовано и работает; **частично** — реализовано не полностью или с условными данными;
**нет** — не реализовано. «Не проверено» — реализация есть в коде, но в этой сессии не испытывалась.

программа «Экшн · 62 с» — динамичный вариант. Повторно реализовывать не требуется; ниже — сверка с критериями приёмки.

## 3. Постоянные инструкции: как соблюдаются в процессе разработки

| Требование | Как обеспечено |
|---|---|
| Сохранение существующего проекта, без перестройки с нуля | рефакторинг с проверкой отпечатком сцены и данных (`tools/fingerprint.mjs`) до и после каждого шага |
| Не выдавать условное за подтверждённое | пометки «условно» в данных и интерфейсе; модельные данные помечены; правило в CLAUDE.md |
| Технологическую схему не менять без согласования | граф ТП в `data/26-proc-graph.PROC.json`, модульные тесты маршрутов (`tests/proc-logic.test.mjs`) |
| Разделение логики и визуализации | расчёт не читает сцену (`SIMGEO`), чистые ядра HYD35 и procLogic покрыты тестами |
| Не утверждать, что тест пройден, если не выполнялся | в отчётах указывается, что проверено и чем, и что не проверено |
| Полный готовый HTML на выходе | `npm run build` → один автономный файл; CI выкладывает его в Artifacts |
| Не создавать нерабочих кнопок | смоук-тест открывает все панели; мобильная проверка — меню |

## 4. Роль эксперта (системная роль)

Учтено как требование к стилю и содержанию: терминология АСУ ТП / ПАЗ / СКАДА, системное изложение, связи
«Склад → Узел/Зона → Единица оборудования → Параметры» в паспортах. Реестр документов и паспорта оборудования (`27-dxd.js`)
уже построены по этой иерархии (объект → документы → строки паспорта со статусом подтверждения).

## 6. Риск: репозиторий публичный

Репозиторий `new-rep` публичный. В нём уже находятся сканы проектной документации (`assets/scans/`, `assets/docs/`),
паспорта оборудования и сама модель объекта инфраструктуры. Комплект ПТ (PDF) и персональные сведения об авторе
в репозиторий **не включены** до решения владельца. Рекомендация — сделать репозиторий приватным
(GitHub → Settings → General → Danger Zone → Change visibility); после этого исходные документы можно хранить в `docs/source/`.

## 7. Рекомендуемый порядок работ

1. Решение по видимости репозитория (раздел 6).
2. Подземные сети В2/В10 по 610-ПТ-001/004/006/007: проектные глубины по профилю и колодцам, диаметры колец — снять пометку «условно» там, где данные подтверждены (данные, не код: `data/19-pipe-registry-data.UG_DATA.json`, `UGND_DEPTH`).
3. Насосная станция пожаротушения 644 по 644-ПТ: паспорт оборудования (реестр документов) и, по согласованию, 3D-компоновка.
4. Кинорежим: сцена насосного цеха 200; испытание записи MP4.
5. Обучающие задания при обходе (контрольные точки, вопросы, поиск неисправностей) — раздел 6 контекста.
6. Аварийные сценарии с действиями персонала — разделы 7–8 контекста (крупная работа, требует согласования объёма).
